第 12 章：排障与最佳实践（数据质量×吞吐×数值稳定的交叉坑位）

12.1 开篇段落

在将一个小模型从零训练到可流畅对话的过程中，最耗时、最令人沮丧的往往不是编写前向传播的架构，而是排查那些“模型能跑通，但结果不对”的幽灵问题。当你满怀期待地启动 runs/speedrun.sh，却在几个小时后发现训练速度突然断崖式下降、显存莫名其妙地溢出（OOM）、损失函数（Loss）曲线上出现触目惊心的尖刺，或者模型在最终评测时只能输出无限循环的乱码时，你便进入了深度学习工程中最具挑战性的“深水区”。

大语言模型（LLM）的训练是一个高度耦合的复杂系统。一个表面上的“数值发散”问题，其根源可能并非学习率设置过高，而是由于数据预处理时的分词器（Tokenizer）截断逻辑错误，导致模型接收到了全为填充符（Padding）的异常批次；一个表面上的“显存溢出”问题，可能不是因为模型太大，而是由于评估阶段的键值缓存（KV Cache）没有及时释放。因此，问题的根源往往潜伏在数据质量、硬件吞吐与数值稳定性的交叉地带。

本章旨在为你提供一套系统性、可操作的排障方法论。我们将 nanochat 链路中常见的坑位梳理为详尽的检查清单（Checklist）与经验法则（Rule-of-thumb）。通过本章的深入学习，你将掌握如何利用系统指标与数学直觉快速隔离问题边界，并在遇到异常时采取正确的兜底、诊断与恢复策略。记住排障的第一性原理：永远不要在复杂的全量分布式环境中盲目调试；控制变量，先回退到已知的、最小的可运行基线（如单机单卡、极小的数据集、小深度配置），复现问题后再逐步叠加系统的复杂度。

12.2 交叉坑位与排障链路

在 nanochat 的端到端流水线中，异常情况通常可以归结为三大类：吞吐与显存瓶颈、数值与优化发散、数据对齐与静默错误。我们将逐一拆解这些交叉坑位的底层逻辑与排查链路。

12.2.1 吞吐与显存（OOM 与慢）

显存溢出（Out of Memory, OOM）是模型训练中最直观、也最容易让人产生挫败感的错误。要彻底解决 OOM，我们必须在数学和物理层面理解显存的消耗去向。

在混合精度（如 BF16 权重 + FP32 优化器状态）训练中，单张 GPU 的理论显存占用 $M_{total}$ 可以近似分解为四个部分：

$$ M_{total} = M_{weights} + M_{gradients} + M_{optimizer} + M_{activations} $$

  1. 模型权重 ($M_{weights}$)：如果参数量为 $\Phi$，使用 BF16（2 字节），则占用 $2\Phi$ 字节。
  2. 梯度 ($M_{gradients}$)：与权重同精度，占用 $2\Phi$ 字节。
  3. 优化器状态 ($M_{optimizer}$)：对于标准的 AdamW 优化器，需要保存 FP32（4 字节）的动量（Momentum）和方差（Variance），以及一份 FP32 的主权重副本用于高精度更新。因此占用 $4\Phi + 4\Phi + 4\Phi = 12\Phi$ 字节。
  4. 激活值 ($M_{activations}$)：这是前向传播中产生并为反向传播保留的中间张量。其大小与批次大小（Batch Size, $B$）、序列长度（Sequence Length, $T$）、隐藏层维度（Hidden Size, $H$）以及层数（Layers, $L$）呈正相关。

经验法则（Rule-of-thumb）：

静态显存（权重+梯度+优化器）对于一个给定大小的模型是固定的（通常为 $16\Phi$ 字节）。当你遇到 OOM 时，唯一能大幅动态调整的只有激活值显存。

在 nanochat 中，总批次大小（Total Batch Size, $B_{total}$）决定了模型在参数空间中优化的轨迹，它的等式为： $$ B_{total} = B_{device} \times N_{devices} \times S_{accum} $$ 其中 $B_{device}$ 是单卡微批次大小，$N_{devices}$ 是 GPU 数量，$S_{accum}$ 是梯度累加步数。

排障链路：应对 OOM 当遇到 OOM 时，最安全且不改变数学收敛轨迹的做法是：将 $B_{device}$ 减半，同时将 $S_{accum}$ 翻倍。 这样 $B_{total}$ 保持不变。如果即便 $B_{device}=1$ 依然 OOM，则说明静态显存或单条序列的激活值已经超出了物理显存，此时必须考虑引入激活重计算（Activation Checkpointing/Gradient Checkpointing）或降低序列长度 $T$。

排障链路：应对训练极慢（吞吐瓶颈） 如果训练没有 OOM，但每秒处理的 Token 数（Tokens per second）远低于硬件理论上限，你需要观察 GPU 的利用率（Utilization）曲线：

12.2.2 数值稳定性（Loss 尖刺与发散）

预训练和 SFT 过程中，Loss 突然飙升（Spike）或直接变成 NaN（Not a Number）是极其破坏性的。一旦出现 NaN，整个网络的权重会被污染，训练只能从之前的 Checkpoint 重启。

Loss 尖刺通常由以下几个深层因素引起：

  1. 学习率过高或预热（Warmup）不足：在训练初期，模型参数处于随机初始化状态。如果此时学习率（$\eta$）过大，梯度更新步长过长，会将参数推向损失函数极度陡峭的区域。
  2. 极端的异常数据：例如某一条样本全为特殊符号，或者在 SFT 中某条样本的有效回复极短，导致该 Batch 的平均 Loss 极高，产生巨大的梯度。
  3. 低精度计算溢出：在使用 FP8 或 BF16 混合精度时，由于数值表示范围有限，前向传播中的指数运算（如 Softmax）或反向传播中的梯度累加极易发生上溢（Overflow）或下溢（Underflow）。

我们可以通过监控梯度范数（Gradient Norm, $|g|$）来提前预警数值不稳定： $$ |g| = \sqrt{\sum_{i=1}^{N} (\nabla \theta_i)^2} $$ 当 $|g|$ 呈现指数级放大时，通常意味着即将发生 Loss 尖刺。

[Loss 尖刺与梯度范数监控图示]

Loss 曲线:
      |          /\ (Spike!)
      |         /  \
      |        /    \
      |-------/      \-------- (恢复或发散)
      +-------------------------> 步数 (Steps)

应对策略：梯度裁剪 (Gradient Clipping)
当 ||g|| > c 时，强制缩放梯度：
g <- g * (c / ||g||)

排障决策树： 遇到 Loss 尖刺时，请严格按照以下顺序排查：

  1. 检查梯度范数日志：如果尖刺发生前 $|g|$ 急剧放大，说明遇到了陡峭的损失平面。确认是否开启了梯度裁剪（通常阈值设为 $1.0$）。
  2. 检查最近的数据流：打印出尖刺发生前 5 个 Batch 的文本内容。看是否包含大量未截断的乱码、全 Padding 序列，或者语言极其罕见的数据。
  3. 检查计算精度（FP8/BF16）：如果数据和超参都没问题，暂时关闭 FP8，回退到纯 BF16 运行数百步。如果 Loss 恢复平稳，说明是 FP8 的缩放因子（Scaling Factor）更新滞后导致的数值溢出。
  4. 回退与跳过：从尖刺发生前约 500 步的 Checkpoint 恢复，并手动修改 DataLoader 的随机数种子或步数偏移，以跳过那段可能含有“毒药数据”的区域，同时略微降低学习率。

12.2.3 数据质量与对齐（静默错误）

相比于直接报错的 OOM 或 NaN，静默错误（Silent Failures）更加致命。模型正常收敛，Loss 曲线平滑下降，吞吐量极高，但最终在 CORE 评测或实际对话时，指标极差，甚至只会输出乱码。这通常是数据准备与对齐阶段的逻辑漏洞导致的。

  1. Masking 错误（掩码反转或全局误杀） 在 SFT（监督微调）阶段，我们希望模型学习“根据用户的 Prompt 生成助手的 Response”。因此，计算交叉熵损失（Cross-Entropy Loss）时，必须忽略 Prompt 部分的 Token，只对 Response 部分求 Loss。 如果掩码逻辑写错，把 Response 也 Mask 掉了，Loss 会迅速降到接近 $0$（因为所有标签都被设为了忽略值，如 -100），模型看似“秒收敛”，实则什么都没学到。
[SFT 掩码逻辑图示]

文本:  [BOS] 用户: 你好！ [EOS] 助手: 你好，我是 nanochat。 [EOS]
Token:   1    45   67  89   2    102  105 200  345   678    2
Label: -100 -100 -100 -100 -100  105  200 345  678    2   -100

* 注意：助手的第一个 Token (102) 的预测目标是 105，因此 105 是有效标签。
* 最后一个 [EOS] 的标签必须保留，否则模型学不会停止生成！
  1. Packing 截断与注意力污染 为了提高预训练吞吐，我们会将多条短数据打包（Packing）成固定长度 $T$ 的序列。如果仅仅是拼接文本，而不修改注意力掩码（Attention Mask），模型在计算自注意力时，后一篇文章的开头会“看到”前一篇文章的结尾，学到错误的上下文关联（即注意力污染）。

正确的 Packing 必须配合块对角因果掩码（Block-Diagonal Causal Mask）：

经验法则（Rule-of-thumb）：

永远不要盲目相信你的数据处理代码。 在正式启动任何训练前，编写一个极其简单的脚本，从 DataLoader 中抽取前 5 个 Batch。将输入张量反向解码（Decode）为人类可读的文本，并将对应的 Label 张量对齐打印出来。用肉眼逐字检查特殊 Token（如 [BOS]、[EOS]、<|im_start|>）的位置，以及 -100 掩码是否精确覆盖了不需要计算 Loss 的部分。

12.3 本章小结

本章系统探讨了模型训练中排障的核心方法论。请将以下关键概念与公式作为你的排障工具箱：

  1. 批次等式与收敛一致性： $$ B_{total} = B_{device} \times N_{devices} \times S_{accum} $$ 在解决 OOM 时，通过调节 $B_{device}$ 和 $S_{accum}$ 保持 $B_{total}$ 不变，是维持优化轨迹的铁律。

  2. 显存消耗的数学直觉： $$ M_{total} = M_{weights} + M_{gradients} + M_{optimizer} + M_{activations} $$ 理解静态显存（通常为 $16\Phi$ 字节/参数）与动态激活显存的边界，是决定是否需要激活重计算的关键。

  3. 数值稳定性的监控： 监控梯度范数 $|g|$。当 $|g|$ 异常放大时，依赖梯度裁剪公式 $g \leftarrow g \cdot \frac{c}{\max(|g|, c)}$ 进行兜底，并结合 Checkpoint 回退与数据跳过策略恢复训练。

  4. 防范静默错误的第一性原理： 数据准备的任何微小瑕疵（如 EOS 缺失、Mask 偏移、Packing 注意力污染）都会在训练后被无限放大。肉眼反向解码检查 DataLoader 的输出，是消除静默错误的唯一可靠手段。

12.4 练习题

  1. 基础题：应对突发的 OOM 在不改变模型架构（层数、维度）和序列长度 $T$ 的前提下，你的单机 8 卡训练脚本在第 500 步突然抛出 CUDA Out of Memory 错误。当前配置为：--device-batch-size 4，--grad-accum-steps 2。请说明应如何修改这两个参数以绕过 OOM，同时保证模型在数学上的收敛轨迹绝对不变？ Hint：回顾批次等式，计算当前的总批次大小，并思考显存占用与哪个参数直接相关。
查看答案

当前的理论总批次大小为：$B\_{total} = 4 \times 8 \times 2 = 64$。为了降低显存峰值，必须减小单次前向/反向传播处理的数据量，即降低设备微批次大小。我们可以将 `--device-batch-size` 减半为 2。为了保持总批次大小 64 不变，必须等比例增加梯度累加步数，即将 `--grad-accum-steps` 翻倍为 4。这样，单卡的激活值显存占用减半，有效绕过了 OOM，而优化器每次更新时依然是基于 64 个样本的平均梯度，数学收敛轨迹保持一致。

  1. 基础题：SFT 训练 Loss 异常偏低 在进行对话微调（Chat SFT）时，你发现第一步的 Loss 就直接降到了 $0.001$ 左右的极小值，且后续几百步几乎不再下降。训练结束后，模型在推理时只会输出空白或无意义的重复乱码。这最可能是数据准备阶段的什么错误导致的？ Hint：思考交叉熵损失函数的计算分母，以及在 SFT 中哪些 Token 的标签被设为了 -100（忽略值）。
查看答案

这属于典型的“全局误杀”静默错误。最可能是掩码（Masking）逻辑出现了严重偏差。在 SFT 中，通常只对助手（Assistant）的回复部分计算 Loss，而将用户提示（Prompt）和填充（Padding）部分的标签设为 `-100` 以忽略计算。如果代码逻辑错误（例如把寻找助手起始符的索引写错了），导致将整条序列（包括助手的回复）的标签全部设为了 `-100`，那么计算出的 Loss 就会接近 0（因为没有有效的 Token 参与交叉熵计算）。模型实际上没有收到任何有效的梯度更新信号，权重保持在预训练状态或被微弱的噪声破坏，因此推理时输出乱码。

  1. 基础题：吞吐量随时间下降的系统瓶颈 训练开始时，系统的吞吐量稳定在 5000 Tokens/sec。但随着训练步数增加到数万步，吞吐量呈现缓慢但持续下降的趋势（降至 3000 Tokens/sec），且通过监控发现 GPU 利用率逐渐出现周期性的低谷（锯齿状）。请指出两种可能导致该现象的系统级原因。 Hint：思考长时间运行的 Python 进程中，内存管理、数据读取机制以及磁盘 I/O 可能发生什么变化。
查看答案

这种现象通常表明系统瓶颈从 GPU 算力转移到了 CPU 或数据 I/O 上。可能的原因包括：第一，DataLoader 的内存泄漏或 CPU 内存碎片化。如果数据预处理逻辑中包含了不断增长的列表追加操作，或者使用了未正确释放内存的第三方库，会导致 CPU 准备 Batch 的时间越来越长，从而“饿死” GPU。第二，磁盘 I/O 缓存命中率下降。随着数据集的随机读取（Shuffle）深入，操作系统层面的 Page Cache 可能被耗尽，导致后续的数据读取频繁触发底层的慢速磁盘 I/O 操作，使得数据加载延迟增加。

  1. 基础题：推理阶段的无限生成幻觉 你使用训练好的 nanochat 模型进行对话推理。当你输入“请介绍一下相对论”时，模型能够正确且流利地回答出相对论的核心概念。但在回答结束后，模型并没有停止，而是继续输出诸如“\n\n用户：那量子力学呢？\n\n助手：量子力学是...”的幻觉对话，直到触发了最大生成长度限制（Max New Tokens）才被迫截断。这是为什么？ Hint：自回归模型依靠什么明确的信号来决定停止生成？训练数据中是否缺少了某种约束？
查看答案

这是因为模型没有学到“何时闭嘴”的明确信号。具体原因通常有两个层面：在 SFT 数据准备阶段，没有在助手回复的真实文本末尾正确追加结束符（如 [EOS] 或 <|im_end|>），或者在计算 Loss 时错误地将结束符 Mask 掉了，导致模型没有将结束符与对话完成的语义绑定；另一方面，在推理引擎（Engine）的生成循环中，可能没有将该特殊的 EOS Token ID 正确配置为停止条件（Stopping Criteria）。因此，模型只能根据预训练阶段学到的海量文本规律，顺理成章地继续续写后续可能出现的对话格式。

  1. 挑战题：Loss 尖刺后的稳妥恢复策略 在进行大规模预训练时，第 10000 步的监控面板上出现了严重的 Loss 尖刺，梯度范数飙升，随后第 10005 步的 Loss 变成 NaN，训练彻底崩溃。你手头有第 9000 步、9500 步和 9900 步的 Checkpoint。请描述一个稳妥的恢复训练流程，以确保模型能够健康地继续训练。 Hint：直接从 9900 步恢复可能会再次遇到同样的问题（因为即将遇到“毒药数据”或优化器状态已不稳定）。需要综合考虑优化器状态、数据跳过与学习率预热。
查看答案

稳妥的恢复策略需要“退一步海阔天空”。首先，绝对不能直接从 9900 步恢复，因为此时优化器状态（如 Adam 的动量和方差）可能已经积累了大量异常的偏置值，且很可能即将再次读取到导致崩溃的“毒药数据”。正确的流程是：第一步，退回到 9500 步（甚至 9000 步）的健康 Checkpoint；第二步，通过调整 DataLoader 的随机数种子（Seed）或手动设置步数偏移（Skip Steps），强行跳过 9500 到 10000 步之间的数据，以避开潜在的异常样本；第三步，在恢复训练的初期，手动介入学习率调度，将当前学习率降低一半，并重新进行短暂的预热（Warmup）；第四步，密切观察恢复后的几百步，若梯度范数保持平稳，再逐渐将学习率恢复到原有的衰减曲线上。

  1. 挑战题：验证 Packing 逻辑与注意力掩码的正确性 为了极大提升预训练的吞吐效率，你引入了一种 Best-fit Packing 算法，将多段长度不一的短文本拼接成长度恰好为 $T=4096$ 的序列。由于拼接了多篇文章，你必须修改标准的下三角注意力掩码。请设计一种无须实际启动模型训练的验证方法，来确保你的 Packing 逻辑和自定义的 Attention Mask 矩阵是绝对正确的。 Hint：可以利用肉眼检查反向解码的文本边界，并结合矩阵可视化的方式断言掩码的块对角特性。
查看答案

验证分为文本边界验证和矩阵拓扑验证两步。首先，从修改后的 DataLoader 中抽取几个 Batch 的输入 Token ID，将其反向解码为文本。肉眼仔细检查在不同文档的拼接处，是否正确插入了分隔符（如 [EOS]）。其次，提取对应的 Attention Mask 矩阵（通常是一个 $4096 \times 4096$ 的布尔矩阵）。使用可视化工具（如 Matplotlib）将其绘制为黑白图像。正确的掩码矩阵必须呈现“块状下三角”结构（Block-Diagonal Causal Mask）：在同一篇文档内部，呈现标准的下三角形状（允许看到当前及之前的 Token）；而在文档边界处，掩码必须被严格阻断，即后一篇文档的任何 Token 对应的行，在对应前一篇文档列的位置上，必须全部为 0（表示不可见）。编写断言（Assert）脚本自动检查矩阵中是否存在跨文档的非法注意力连线即可。

  1. 挑战题：RL 阶段的 Reward Hacking 排查与修正 在运行强化学习（如基于 GRPO 的 RL）以优化模型的数学推理能力（如 GSM8K 任务）时，你观察到训练曲线非常漂亮：模型在训练集上的 Reward 分数稳步上升。但在独立的测试集上评估时，准确率反而显著下降了。你抽取了模型生成的推理过程，发现模型学会了输出极长、充满无意义的重复推导（如“1+1=2，所以2+2=4，所以...”），偶尔在最后碰巧带上正确答案的标签。应如何从奖励函数和数据层面修正这个问题？ Hint：思考强化学习中模型是如何“钻空子”的。奖励函数的设计是否存在漏洞？如何通过惩罚项或格式约束来规范模型的行为？
查看答案

这是强化学习中极其经典的“奖励作弊”（Reward Hacking）现象。模型发现，只要输出足够长，随机命中正确答案格式或包含正确数字的概率就会增加，从而骗取奖励。修正方法需要多管齐下：第一，在奖励函数中引入长度惩罚（Length Penalty），对超出合理推导长度的输出给予负反馈扣分；第二，增加严格的格式奖励（Format Reward），要求模型必须按照特定的标签结构（例如，思考过程必须包裹在 <think>...</think> 中，最终答案必须在 <answer>...</answer> 中）进行输出，任何格式错乱直接给予强烈的负奖励（如 -1.0）；第三，回到数据层面，确保在进入 RL 阶段之前，模型已经通过高质量的 SFT 数据固化了基础的推理输出格式，RL 只是用来探索更优的解题路径，而不是从零学习如何说话。

  1. 挑战题：FP8 混合精度下的静默精度损失 为了追求极致的训练速度，你在预训练中开启了 FP8 混合精度计算。监控显示吞吐量成功翻倍，且 Loss 曲线看似正常下降。但训练结束后，模型在生成文本时显得极其“愚蠢”，词汇多样性极差，甚至频繁重复同一个词。你怀疑是 FP8 导致了静默的精度损失。请说明在 Transformer 架构中，哪些关键组件绝对不能使用 FP8 计算，并解释其背后的数值直觉。 Hint：FP8 的动态范围极小。思考 Transformer 中哪些操作涉及极大的数值差异（如指数运算）或需要高精度的累加。
查看答案

FP8 的数值动态范围（无论是 E4M3 还是 E5M2）都非常有限，极易在差异巨大的数值计算中发生下溢（变为 0）或上溢（变为 NaN）。在 Transformer 中，绝对不能使用 FP8 的组件包括：第一，注意力机制中的 Softmax 操作。Softmax 涉及指数运算，如果输入差异稍大，低精度下较小的值会被直接抹零，导致注意力分布变得极其尖锐（类似 One-hot），模型丧失了捕捉长距离依赖的能力；第二，最后的语言模型头（LM Head）。它需要将隐藏状态映射到数万维的词表空间并计算概率，低精度会导致大量低频词的对数几率（Logits）无法区分，从而严重破坏词汇多样性；第三，所有的层归一化（LayerNorm/RMSNorm）及残差连接的累加操作。这些操作需要保持高精度的方差统计和微小的梯度累加，必须保留在 BF16 或 FP32 精度下。FP8 仅适合用于主干的密集矩阵乘法（Linear 层的 GEMM 操作）。

12.5 常见陷阱与错误 (Gotchas)

在 nanochat 的开发与调试过程中，以下陷阱曾让无数工程师耗费数个日夜。请将它们作为你排障时的首要检查项：

  • 陷阱：DDP 中的 find_unused_parameters 性能黑洞 在分布式数据并行（DDP）训练时，如果你在初始化时开启了 find_unused_parameters=True，PyTorch 会在每次反向传播前遍历整个计算图以寻找未参与前向传播的参数。这在复杂的模型（尤其是包含大量条件分支的模型）中会引发极大的 CPU 开销，导致吞吐量骤降。 对策：在预训练和标准的 SFT 中，所有参数都应该参与计算。永远确保 find_unused_parameters=False。如果确实有未使用的参数（如某些特殊的 Embedding 没用到），应从模型架构设计上将其剔除，而不是依赖 DDP 去动态查找。

  • 陷阱：Tokenizer 特殊符号的“训练-推理”不一致 在 SFT 训练时，你使用了 <|im_start|> 和 <|im_end|> 作为对话轮次的标记，并且模型成功收敛。但在推理时，你发现模型无法正确识别用户的 Prompt。排查后发现，推理脚本中的 Tokenizer 配置没有将这两个符号注册为 special_tokens，导致它们被当成了普通的纯文本（例如被切分成了 <、|、im、_ 等多个无意义的碎片 Token）。 对策：特殊 Token 的生命周期必须贯穿始终。确保在训练前、评估时和推理引擎中，Tokenizer 的 added_tokens 字典是完全对齐的，并且在生成逻辑中正确配置了 stop_token_ids。

  • 陷阱：恢复训练时的随机数种子错位与数据重放 从 Checkpoint 恢复训练时，Loss 曲线出现了不自然的抖动，或者在恢复后的几个 Epoch 内模型性能没有提升。这往往是因为恢复时只加载了模型权重和优化器状态，而没有正确恢复 DataLoader 和随机数生成器（RNG）的内部状态。导致模型重新看到了之前已经训练过的数据（数据重放），或者跳过了本该学习的数据。 对策：一个健壮的 Checkpoint 机制必须保存 torch.get_rng_state()、numpy.random.get_state() 以及数据采样器（Sampler）走过的步数记录。在恢复时，严格对齐这些状态，确保数据流的绝对连续性。

  • 陷阱：评估阶段 KV Cache 导致的隐性 OOM 训练过程非常顺利，但在每个 Epoch 结束触发 CORE 评测（生成长文本）时，程序突然 OOM 崩溃。这是因为在自回归生成时，推理引擎会维护一个不断增长的键值缓存（KV Cache）以加速计算。如果没有设置最大生成长度限制，或者在评估多个样本时没有及时清空上一轮的 Cache，显存会被迅速耗尽。 对策：在评估脚本中，务必使用 torch.no_grad() 上下文管理器，明确设置 max_new_tokens，并在每个评估 Batch 结束后显式调用缓存清理逻辑（如重新初始化 Engine 的状态），必要时调用 torch.cuda.empty_cache() 回收显存碎片。

  • 陷阱：过度记录（Logging）拖垮吞吐 为了详细监控训练过程，你在每一步（Step）都调用了 Wandb 记录几十个标量，甚至记录了生成的文本样本和注意力热力图。结果发现，原本应该毫秒级完成的 Step 被拖长到了数秒，GPU 利用率惨不忍睹。 对策：记录操作（尤其是涉及将张量从 GPU 显存拷贝到 CPU 内存的 .item() 或 .cpu() 操作）会严重阻塞 CUDA 的异步执行流。采用“对数间隔”或“固定步数间隔”记录策略：例如标量 Loss 每 10 步记录一次，文本样本每 500 步记录一次，并且尽量将日志数据的聚合操作放在后台线程异步处理。
