第 3 章：预训练数据（FineWeb-Edu shards：下载、切分、shuffle、parquet 约定）

在预训练阶段，数据就是模型的“食物”，而数据流水线（Data Pipeline）则是为 GPU 供餐的传送带。对于一个端到端的精简系统而言，如何高效地获取、存储并向模型喂养这些食物，直接决定了训练的吞吐量（Tokens per second）和最终的模型效果。在实际的工程实践中，往往有超过一半的训练故障（如 GPU 饥饿、损失函数发散、分布式死锁）根源于数据处理的不当。

本章将深入探讨 nanochat 中预训练数据的生命周期：从云端的 FineWeb-Edu 数据集，到本地的 Parquet 分片（shards），再到训练集与验证集的严格物理划分，以及保证数据分布均匀的 Shuffle 策略。学习本章后，你将能够以数据工程师的视角，彻底掌控预训练语料的流转机制，并为后续的 Tokenization 和 Packing 阶段打下坚实的基础。

3.1 为什么选择 FineWeb-Edu 与 Parquet 格式

在设计 nanochat 的“最小全流程”时，我们面临的第一个决策是：用什么数据来训练基础模型（Base Model）？在动辄数万亿 Token 的大模型时代，单机单节点跑通全流程需要一种“极高信息密度”的语料。

3.1.1 FineWeb-Edu 的高信息密度

nanochat 的默认配置强约定使用 FineWeb-Edu 数据集（具体为 sample-10BT 或更小的子集）。FineWeb-Edu 是基于 CommonCrawl 网页数据，通过极其严格的质量过滤流程（包括启发式规则去重、语言识别），并最终使用“LLM-as-a-Judge”（大语言模型作为裁判）技术，为每个网页打上“教育价值分数”后筛选出的高质量子集。

这种高密度的教育类文本具有以下特性：

  1. 长上下文连贯性：相比于零碎的社交媒体短文本，教育类网页（如维基百科、学术博客、教程）通常具有完整的逻辑推演过程。
  2. Scaling 效率极高：在相同的参数量和训练 Token 数下，使用 FineWeb-Edu 训练的模型在常识推理、阅读理解等基准测试（如 MMLU、HellaSwag）上的表现，显著优于使用未经严格过滤的原始网页数据训练的模型。

3.1.2 Parquet：为吞吐量而生的列式存储

面对海量文本的存储与读取，常见的数据格式（如 JSONL 或 CSV）在预训练场景下暴露出严重的性能瓶颈。nanochat 强约定使用 Parquet 格式进行数据落盘。

Parquet 是一种开源的列式存储（Columnar Storage）格式，具有极高的压缩比和读取效率。我们可以通过下面的 ASCII 图来直观对比行式存储与列式存储在读取时的差异：

【行式存储（如 JSONL）的读取路径】
磁盘文件：
{"id": 1, "url": "http...", "text": "Hello world", "score": 5}
{"id": 2, "url": "http...", "text": "Deep learning", "score": 4}
   │
   ▼

1. 磁盘 I/O：读取整行所有字节（包含无关的 id, url, score）
2. CPU 解析：反序列化整个 JSON 对象
3. 内存提取：提取 "text" 字段，丢弃其他字段（产生大量内存碎片和垃圾回收开销）
结论：I/O 浪费严重，CPU 成为解析瓶颈。

【列式存储（如 Parquet）的读取路径】
磁盘文件（按列连续存储）：
[Column: id]    1, 2, ...
[Column: url]   "http...", "http...", ...
[Column: text]  "Hello world", "Deep learning", ...
[Column: score] 5, 4, ...
   │
   ▼

1. 磁盘 I/O：直接定位到 "text" 列的物理偏移量，仅读取文本字节流
2. CPU 解析：直接解压（如 Snappy/Zstd）并映射到内存数组
结论：I/O 利用率达到极致，CPU 开销极低。

在预训练场景下，数据加载器（DataLoader）绝大多数时候只关心文本内容本身。Parquet 允许 DataLoader 实现投影下推（Projection Pushdown），即只把需要的列从磁盘搬到内存，这使得磁盘 I/O 压力成倍下降，确保 GPU 不会因为等待数据而处于饥饿状态。

经验法则（Rule-of-Thumb）：

永远不要在训练循环中实时解析 JSONL。如果你拿到的是 JSONL 数据，第一步必须是写一个离线脚本，将其转换为按块（Block）压缩的 Parquet 文件。这不仅能节省 50% 以上的磁盘空间，更能提升 3-5 倍的读取吞吐量。

3.2 数据分片（Sharding）的艺术

面对数十亿甚至上百亿 Token 的语料，将所有数据塞进一个巨大的文件中是不现实的。单文件会导致无法并行下载、无法在内存受限的机器上处理，并且在分布式文件系统中极易造成单点热点。因此，nanochat 采用了严格的分片（Sharding）机制，将全量数据切割成多个大小适中的 Parquet 文件（即 Shards）。

3.2.1 分片的数学逻辑

假设我们有一个包含 $N$ 条文档的总数据集，为了平衡 I/O 性能和内存占用，我们期望每个分片文件在未压缩状态下的大小约为 $S_{target}$（例如 $100 \text{ MB}$ 到 $500 \text{ MB}$）。假设每条文档的平均字节数为 $\bar{B}$，那么每个分片包含的文档数 $M$ 大致为：

$$M \approx \lfloor \frac{S_{target}}{\bar{B}} \rfloor$$ 总分片数 $K$ 则可以表示为： $$K = \lceil \frac{N}{M} \rceil$$

在 nanochat 的标准约定中，分片文件通常被命名为 shard_00000.parquet 到 shard_00999.parquet。这种固定长度的零填充（Zero-padding）命名法非常重要，它保证了在任何文件系统或按字母顺序排序的列表中，分片的物理顺序与逻辑顺序绝对一致。

3.2.2 分片机制的三大核心优势

  1. 内存友好（Memory Friendly）：在任何给定的训练时刻，DataLoader 只需要将当前正在处理的少数几个分片加载到内存中。这意味着即使你的数据集高达数 TB，你的内存峰值占用也可以稳定控制在几个 GB 以内，彻底杜绝了 OOM（Out of Memory）的风险。
  2. 断点续传与恢复（Resumability）：在漫长的预训练过程中，硬件故障或被高优先级任务抢占是常态。分片机制使得训练状态的保存变得极其轻量。检查点（Checkpoint）只需要记录两个整数：current_shard_index 和 row_index_within_shard。当系统恢复时，直接从失败的分片和对应行继续读取，避免了从头遍历庞大单文件的巨大开销。
  3. 全局 Shuffle 的基石：在不占用海量内存的前提下，分片是实现近似全局数据随机性的唯一可行路径（详见 3.5 节）。

下面是数据从云端到被加载的物理流转与分片映射示意图：

[ 云端 HuggingFace Hub / S3 ]
          │ (多线程并发下载)
          ▼
[ 本地缓存 NANOCHAT_BASE_DIR/base_data/ ]
  ├── shard_00000.parquet  ─┐
  ├── shard_00001.parquet   │
  ├── shard_00002.parquet   │ 训练集 (Train Split)
  ├── ...                   │ (供 DataLoader 循环读取)
  ├── shard_00989.parquet  ─┘
  │
  ├── shard_00990.parquet  ─┐
  ├── ...                   │ 验证集 (Val Split)
  └── shard_00999.parquet  ─┘ (仅供 Eval 阶段读取)
          │
          ▼
[ 数据加载器 DataLoader ]
  (按 Shuffle 策略抽取 Shard -> 提取文本 -> 交给 Tokenizer)

经验法则（Rule-of-Thumb）：

分片大小（Shard Size）是一个关键的超参数。如果分片太小（如 1MB），会导致频繁的文件打开/关闭操作，引发严重的文件系统元数据开销（Metadata Overhead）；如果分片太大（如 10GB），会导致内存吃紧，且打乱（Shuffle）的粒度变粗。推荐的单分片大小为 100MB 到 500MB。

3.3 本地缓存与下载约定

在分布式训练或频繁的实验迭代中，重复从公网下载数据是不可接受的。nanochat 遵循“按需下载，本地绝对缓存”的强约定。

所有下载的预训练数据、Tokenizer 模型文件以及评估用的基准数据集，都会默认存放在 ~/.cache/nanochat 目录下。这个行为由核心模块 nanochat/common.py 控制。

源码细节：按需下载的“最小但靠谱”实现

nanochat/dataset.py 把预训练语料视为一组按序编号的 Parquet 分片：文件名形如 shard_00000.parquet，并通过 index -> filename 的纯函数映射来定位。下载逻辑有几个很工程化的小设计，特别适合写进你自己的数据管道复用：

  1. 存在即跳过：如果本地已经有对应 shard，就不会重复下载。
  2. 先写临时文件再原子替换：下载先落到 .tmp，完整写完再 rename 成正式文件，避免中途中断留下“半个 parquet”污染后续训练。
  3. 指数退避重试：网络抖动或短暂的 5xx 不会直接让整条训练链路失败。

3.3.1 环境变量 NANOCHAT_BASE_DIR

你可以通过设置环境变量 NANOCHAT_BASE_DIR 来无缝覆盖这个默认路径。这在实际的集群环境中是必须的操作。

例如，在你的登录节点上，~/.cache 通常位于容量极小且 I/O 极慢的网络挂载盘（NFS）上。如果你直接在这里解压数百 GB 的 Parquet 文件，不仅会耗尽配额，还会拖垮整个集群的文件系统。正确的做法是在启动脚本中将其指向本地的高速 NVMe 固态硬盘或并行文件系统（如 Lustre 或 GPFS）：

例如：在 runs/speedrun.sh 或你的终端中设置环境变量，形如 export NANOCHAT_BASE_DIR=/mnt/nvme_storage/my_username/nanochat_cache。

3.3.2 避免符号链接（Symlink）地狱

如果你直接使用 HuggingFace 的 datasets 库，它默认会在缓存目录中创建复杂的符号链接和基于哈希值的目录结构。nanochat 的选择更“朴素但可控”：预训练 shards 直接平铺在 NANOCHAT_BASE_DIR/base_data/ 下，训练时从这个目录流式读取，不依赖 HF datasets 的隐藏缓存结构。你所见即所得：目录里有多少个 .parquet，训练就能读到多少个分片。

3.4 训练集与验证集的划分（Train/Val Split）

在机器学习中，我们必须保留一部分模型绝对没有见过的数据来评估其泛化能力（计算 Validation Loss 或 BPB）。在 nanochat 中，预训练数据的切分采用的是分片级别的物理隔离（Shard-level Physical Isolation），而不是在运行时对所有数据进行随机采样切分。

3.4.1 为什么拒绝运行时随机切分？

如果我们将所有文档混合在一起，并在每次运行时随机抽取 1% 作为验证集，会带来两个致命问题：

  1. 数据泄露（Data Leakage）：网页数据中经常包含高度重复的模板文本（如网站导航、免责声明）或相似的段落（如同一篇新闻的不同转载）。如果采用随机切分，训练集和验证集中极有可能包含几乎相同的 N-gram 序列。这会导致验证集上的 Loss 虚低，无法真实反映模型的泛化能力。
  2. 状态不可复现：随机切分依赖于全局随机种子。一旦改变了切分比例或种子，整个训练集的数据分布就会发生变化，导致不同实验之间的指标无法严格对齐。

3.4.2 Shard 级别的物理隔离逻辑

nanochat 的做法极其简单粗暴但安全有效：直接从总分片集合中，截断最后几个分片作为验证集。

假设总共有 $K$ 个分片，我们设定保留 $V$ 个分片用于验证。那么：

  • 训练集（Train Split）：包含分片索引 $0$ 到 $K - V - 1$。
  • 验证集（Val Split）：包含分片索引 $K - V$ 到 $K - 1$。

这种物理隔离确保了训练代码和评估代码读取的是完全不同的物理文件，从根本上杜绝了文件句柄交叉和内存数据污染。只要原始数据在打包成 Shard 之前没有经过刻意的强排序（例如把所有高质量数据都放在了最后），这种切分方式就是无偏且安全的。

3.5 Shuffle 策略：全局与局部的平衡

为了让模型学习到稳健的特征，喂给模型的数据必须是高度随机的。如果按固定顺序喂入某一特定领域的连续文档（例如连续喂入 1000 篇全是关于医学的网页，然后再喂入 1000 篇全是关于编程的网页），模型的参数更新会发生剧烈的震荡，导致严重的“灾难性遗忘（Catastrophic Forgetting）”——模型在学习编程知识时，会迅速遗忘刚刚学过的医学知识。

理想状态下，我们需要对全量 $N$ 条数据进行全局 Shuffle。但当 $N$ 达到十亿级别时，维持一个包含所有索引的全局打乱数组会消耗巨大的内存。因此，nanochat 采用了一种经典的“两级 Shuffle（Two-stage Shuffle）”策略。

3.5.1 第一级：Shard 级别的全局 Shuffle（粗粒度）

在每一个 Epoch（或者每一次完整遍历数据集）开始时，DataLoader 首先获取所有训练集分片的文件路径列表。假设有 $990$ 个训练分片，DataLoader 会使用一个确定的随机种子（Random Seed）对这 $990$ 个文件路径进行全局的 Fisher-Yates 洗牌。

通过这一步，我们确保了模型在宏观时间尺度上，接收到的数据主题是均匀混合的。例如，分片 005、089、912 会被交替读取，而不是按顺序读取。

3.5.2 第二级：Row 级别的内存 Shuffle（细粒度）

仅仅打乱文件顺序是不够的，因为一个 500MB 的分片内部可能依然包含连续爬取的同源网页。因此，当 DataLoader 打开一个被选中的 Shard 时，它不会直接按顺序吐出数据，而是维护一个内存 Shuffle 缓冲区（In-Memory Shuffle Buffer）。

其工作机制如下（ASCII 示意图）：

[ 正在读取的 Shard_089.parquet ]
          │ (顺序读取行)
          ▼
[ Shuffle Buffer (容量: B 条文档，例如 B=10000) ]
  [ Doc 1 ] [ Doc 2 ] ... [ Doc 10000 ]
          │
          │ (当 Buffer 填满时)
          ▼

1. 使用随机数生成器从 Buffer 中随机抽取（Pop）一条文档喂给下游。
2. 从 Shard 中读取下一条新文档，填补 Buffer 中的空位。
3. 循环往复，直到 Shard 读取完毕，最后清空 Buffer。

这种机制被称为 Reservoir Sampling（水库采样）的变体。缓冲区大小 $B$ 是一个关键参数：

  • 如果 $B$ 太小（如 $B=10$），局部随机性极差，模型依然会看到连续的相似文档。
  • 如果 $B$ 太大（如 $B=1000000$），会消耗大量 CPU 内存，抵消了分片机制带来的内存优势。

nanochat 通常将 $B$ 设置为几千到一万之间，这足以打乱单个分片内部的局部聚集效应。

3.5.3 分布式训练下的 Shuffle 陷阱（DDP 同步）

在多卡分布式数据并行（Distributed Data Parallel, DDP）环境下，Shuffle 策略隐藏着一个致命的陷阱。

假设你有 8 张 GPU（Rank 0 到 Rank 7）。如果每张卡的 DataLoader 在进行 Shard 级别的 Shuffle 时，使用了不同的随机种子，那么 Rank 0 可能决定先读 Shard_005，而 Rank 1 决定先读 Shard_089。这看起来似乎没问题，但实际上会导致各卡读取的数据长度不一致，或者在 Epoch 结束时某些卡先读完，某些卡还在等待。更严重的是，如果在恢复训练时各卡的进度不一致，会导致极其复杂的逻辑混乱。

强约定： 在 nanochat 中，所有分布式进程在进行第一级（Shard 级别）Shuffle 时，必须且绝对使用相同的全局 Epoch 随机种子。这样，所有 8 张卡面对的是同一个被打乱的 Shard 列表。然后，通过跨步读取（Strided Reading）或分块读取（Chunking），确保 Rank $i$ 只处理属于自己的那部分数据。

例如，对于打乱后的列表 [Shard_A, Shard_B, Shard_C, Shard_D, ...]：

  • 一种简单的策略是：Rank 0 读取 Shard_A，Rank 1 读取 Shard_B...（按文件分配，要求文件大小绝对均匀）。
  • nanochat 更推荐的策略是：所有 Rank 共同打开同一个 Shard，但 Rank $i$ 只读取该 Shard 中行号满足 row_index % world_size == i 的文档。这样保证了各卡在任何时刻处理的数据分布是绝对一致的。

本章小结

  • nanochat 默认使用高质量的 FineWeb-Edu 作为预训练语料，并强约定采用 Parquet 格式进行高效的列式存储，极大提升了磁盘 I/O 效率。
  • 海量数据被切割成多个大小适中（通常 100MB-500MB）的 Shards，这不仅将内存占用控制在极低水平，还为断点恢复提供了轻量级的状态保存机制。
  • 数据的本地落盘受统一的环境变量 NANOCHAT_BASE_DIR 控制，必须将其部署在高速磁盘（如 NVMe SSD）上以防止 GPU 饥饿。
  • 训练集与验证集的划分是在 Shard 级别进行的物理隔离（例如保留最后 10 个分片作为验证集），彻底避免了运行时的随机切分导致的数据泄露和状态不可复现。
  • 两级 Shuffle 策略（Shard 级的全局洗牌 + 内存 Buffer 的行级洗牌）以极低的内存代价实现了近似全局的数据随机性。在 DDP 环境下，必须保证各进程在 Shard 级别 Shuffle 时使用完全一致的随机种子。

练习题

  1. 基础题：为什么在预训练的数据流中，Parquet 格式比 JSONL 格式具有更高的读取吞吐量？ Hint：思考“投影下推”的概念以及磁盘读取的物理过程。
查看答案

Parquet 是一种列式存储格式，数据在磁盘上是按列连续存放的。在预训练时，DataLoader 只需要文本数据，Parquet 允许系统直接定位并仅读取“文本”这一列的字节流（即投影下推），跳过了所有无关字段（如 URL、ID、时间戳）的 I/O 和解析。而 JSONL 是行式存储，必须将整行完整读入内存并进行昂贵的 JSON 反序列化后，才能提取出文本字段，这造成了极大的 I/O 浪费和 CPU 瓶颈。

  1. 基础题：如果你的服务器系统盘（默认缓存路径所在盘）是机械硬盘，且空间不足，你应该如何处理 nanochat 的数据下载？写出具体的操作逻辑。 Hint：回忆关于本地缓存约定和环境变量的内容。
查看答案

绝对不能将数据下载到机械硬盘上，否则会导致严重的 GPU 饥饿。应该寻找服务器上挂载的高速 NVMe 固态硬盘路径（例如 /mnt/nvme_data/），然后在启动任何 nanochat 脚本或运行 runs/speedrun.sh 之前，通过设置环境变量来覆盖默认路径：export NANOCHAT_BASE_DIR=/mnt/nvme_data/nanochat_cache。这样所有的数据下载、分片和模型缓存都会自动重定向到高速磁盘。

  1. 基础题：在 nanochat 中，训练集和验证集是如何被划分的？这种划分方式相比于 train_test_split(data, test_size=0.01) 有什么优势？ Hint：考虑数据泄露（Data Leakage）和实验的可复现性。
查看答案

采用的是分片（Shard）级别的物理隔离。系统会将总分片集合中的最后几个分片（如最后 10 个）整体划分为验证集，其余分片作为训练集。 优势在于：1. 避免数据泄露。随机切分容易导致同一篇文章的不同段落或高度相似的模板文本同时出现在训练集和验证集中，使得验证指标虚高；物理隔离通常能更好地保持文档的完整性。2. 状态可复现。物理隔离不需要依赖全局随机种子来实时切分，确保了不同实验跑出来的验证集是绝对一致的物理文件，便于公平对比指标。

  1. 基础题：简述 nanochat 中的“两级 Shuffle”策略的具体执行过程。 Hint：分别在文件层面和内存层面做了什么操作？
查看答案

第一级是 Shard 级别的粗粒度 Shuffle：在每个 Epoch 开始前，DataLoader 使用随机种子对所有训练分片的文件名列表进行全局洗牌，决定分片的读取顺序。 第二级是 Row 级别的细粒度 Shuffle：当打开某个分片后，DataLoader 会在内存中维护一个固定大小的缓冲区（如包含 10000 条文档）。它不断从分片中读取文档填入缓冲区，并随机从缓冲区中抽取（Pop）文档喂给下游模型，以此打乱单个分片内部的局部顺序。

  1. 挑战题：假设你的总预训练数据有 1000 亿个 Token，按每个 Token 约 4 字节计算，总数据量约为 400GB。如果将分片大小 $S_{target}$ 设置为极大（例如每个分片 100GB，共 4 个分片），会对训练过程和 Shuffle 产生什么具体的负面影响？ Hint：结合内存限制、两级 Shuffle 的机制以及断点恢复进行深入思考。
查看答案
  1. 局部随机性崩溃：因为只有 4 个分片，第一级的 Shard Shuffle 几乎失去了意义。模型会在很长一段时间内（处理 100GB 数据期间）只看到该分片内的数据分布。受限于内存，第二级的 Row Shuffle Buffer 无法开到 100GB，只能在极小的局部窗口内打乱，导致模型容易陷入局部最优或发生灾难性遗忘。
  2. 断点恢复代价极高：如果训练在处理某个 100GB 分片的 99% 处崩溃，恢复时 DataLoader 可能需要重新遍历并跳过前面 99GB 的数据行才能找到断点，耗时极长。
  3. 内存压力与 I/O 阻塞：打开和解析超大文件容易导致内存峰值飙升，甚至在某些文件系统中引发 I/O 阻塞。
  1. 挑战题：为什么在预训练中，按原始网页爬取的时间顺序依次读取而不做 Shard 级别 Shuffle 会导致模型效果变差？请用数学或优化的直觉解释。 Hint：考虑数据分布的非平稳性（Non-stationarity）对梯度下降轨迹的影响。
查看答案

如果按时间顺序或特定主题顺序读取，喂给模型的批次数据（Batch）将不再是全局数据真实分布的独立同分布（i.i.d.）采样。 从优化直觉来看，梯度下降的方向是由当前 Batch 的损失决定的。如果连续多个 Batch 都是关于“体育”的，模型参数会剧烈地向“体育领域的最优解”移动，从而破坏之前学到的“数学”或“编程”领域的权重（即灾难性遗忘）。这导致模型在参数空间中来回震荡，无法收敛到一个具备通用泛化能力的全局最优解。Shard 级别 Shuffle 强制将不同领域的数据在时间轴上均匀混合，使得每一步的梯度都尽量指向全局最优方向。

  1. 挑战题：假设你有 4 张 GPU 进行分布式数据并行（DDP）训练。为了保证每张卡在同一个 step 拿到的数据不重复且分布均匀，如果采用“所有 Rank 共同打开同一个被打乱的 Shard，然后按行号取模”的策略，各卡的 DataLoader 在初始化时必须绝对保证哪个条件？如果违反了这个条件会发生什么？ Hint：考虑随机种子与 DDP 的集合通信（All-Reduce）。
查看答案

必须绝对保证所有 Rank 的 DataLoader 在进行第一级 Shard Shuffle 时，使用了完全相同的全局随机种子。 如果违反了这一条件（例如各卡用了基于自身进程 ID 的随机种子），Rank 0 可能打开了 Shard_A，而 Rank 1 打开了 Shard_B。由于不同 Shard 的总行数可能不同，或者在 Epoch 结束时某些卡先读完，会导致各卡在进入前向传播或反向传播的 All-Reduce 梯度同步时，部分卡有数据而部分卡没有数据，最终导致整个分布式训练集群发生死锁（Deadlock）并挂起。

  1. 挑战题：在构建 Row 级别的内存 Shuffle Buffer 时，如果你的单条文档长度差异极大（有的只有 10 个 Token，有的有 100,000 个 Token），固定容量为 10,000 条文档的 Buffer 可能会引发什么系统级问题？应如何改进？ Hint：思考固定条数与物理内存占用之间的关系。
查看答案

固定条数（Row-count based）的 Buffer 会导致物理内存占用极不稳定。如果运气不好，Buffer 中同时塞满了 10,000 条长度为 100,000 Token 的超长文档，会导致内存使用量瞬间飙升，直接触发操作系统的 OOM Killer 杀死训练进程。 改进方法：不应该按“文档条数”来限制 Buffer 容量，而应该按“总字节数”或“总 Token 数”来限制（Byte-size based Buffer）。当 Buffer 内积累的数据总大小达到预设的内存阈值（如 2GB）时，就停止读取新文档并开始 Pop，这样可以严格保证内存的安全水位。

常见陷阱与错误 (Gotchas)

  • 陷阱 1：磁盘空间悄悄爆炸（No Space Left on Device）
  • 症状：下载数据或训练中途突然崩溃，报错 OSError: [Errno 28] No space left on device。
  • 根源：预训练数据动辄数百 GB。如果多次中断下载、尝试不同的数据集，或者 HuggingFace 的隐藏缓存机制生成了大量冗余，~/.cache/nanochat 会迅速占满系统盘。

  • 调试与修复技巧：定期使用 du -sh ~/.cache/nanochat/* 检查缓存目录大小。对于不再使用的实验数据分片，及时进行手动清理。强烈建议将 NANOCHAT_BASE_DIR 指向一个拥有 TB 级空间的专用数据盘。

  • 陷阱 2：坏损的 Parquet 分片（Corrupted Parquet File）

  • 症状：训练顺利进行了几个小时，突然抛出 pyarrow.lib.ArrowInvalid: Parquet magic bytes not found 或类似的数据解析错误，进程崩溃。
  • 根源：网络波动可能导致某个 Shard 在云端下载时被截断或损坏，但在文件系统中依然存在且大小看起来正常。DataLoader 读到这个坏损文件的特定偏移量时就会报错。

  • 调试与修复技巧：在正式启动耗资巨大的大规模训练前，写一个简单的预检脚本，使用 pyarrow.parquet.ParquetFile(path).metadata 遍历尝试读取所有 Shard 的 Header 和元数据，提前剔除或重新下载损坏的文件。

  • 陷阱 3：单节点 I/O 瓶颈导致 GPU 饥饿（GPU Starvation）

  • 症状：观察 nvidia-smi，发现 GPU 利用率（Volatile Uncorr. ECC / GPU-Util）忽高忽低，例如在 100% 和 0% 之间呈现锯齿状震荡。
  • 根源：数据加载的速度跟不上 GPU 计算的速度。通常是因为数据存放在了慢速的机械硬盘（HDD）上，或者 DataLoader 的工作进程（num_workers）设置得太少，导致 CPU 无法及时完成 Parquet 的解压和 Shuffle。

  • 调试与修复技巧：首先确认数据挂载在 NVMe SSD 上。其次，在启动脚本中适当增加 DataLoader 的 num_workers（例如设置为 CPU 核心数的一半），并确保开启了 prefetch_factor，让 CPU 提前准备好下几个 Batch 的数据。

  • 陷阱 4：错误的 Shuffle 种子导致 DDP 死锁（DDP Deadlock due to Asymmetric Shards）

  • 症状：多卡训练在某个 Epoch 的末尾，或者在恢复训练后的第一个 Step 突然卡死，GPU 利用率降为 0，程序没有任何报错输出，一直挂起。
  • 根源：正如 3.5.3 节所述，不同 Rank 的 DataLoader 在进行 Shard Shuffle 时使用了不同的随机种子，导致各卡读取的数据序列不同，最终在梯度同步（All-Reduce）时发生死锁等待。

  • 调试与修复技巧：检查 nanochat/dataloader.py 或训练主脚本，确保在初始化 DataLoader 之前，强制调用了类似 set_seed(global_seed) 的函数，保证所有分布式进程在数据打乱逻辑上具有绝对的确定性和一致性。

  • 陷阱 5：验证集被意外污染（Validation Set Contamination）

  • 症状：训练过程中发现验证集上的 BPB（Bits Per Byte）下降得异常快，甚至低于训练集的 BPB，但模型在实际的生成测试中表现极差（只会复读某些特定句式）。
  • 根源：在自定义数据准备逻辑时，没有严格执行物理 Shard 隔离，或者原始数据在打包为 Parquet 之前没有进行彻底的去重（De-duplication），导致大量相同的模板文本同时分布在训练 Shard 和验证 Shard 中。
  • 调试与修复技巧：检查数据切分代码，确保验证集使用的是完全独立的 Shard 索引。如果怀疑数据本身重复率过高，需要回退到数据准备阶段，使用 MinHash 或精确字符串匹配等算法对原始语料进行全局去重。
