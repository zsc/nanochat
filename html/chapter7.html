第 7 章：评估与指标（BPB、CORE、采样；如何读懂 leaderboard）

在小模型的从零训练与微调过程中，如何准确衡量模型的“好坏”直接决定了实验迭代的方向。评估往往是整个大语言模型（LLM）工程中最容易被误解、也最容易引入静默错误（Silent Errors）的环节。本章将带你深入理解 nanochat 评估体系的核心设计哲学：我们将“训练底层信号”与“宏观能力信号”进行明确且严格的剥离。

你将学习到为什么传统的交叉熵损失（Cross-Entropy Loss）在跨越不同词表（Vocabulary）时会彻底失效；BPB（Bits Per Byte）如何借用信息论的基石为你提供一个绝对的压缩率基准；CORE 评测集如何以非生成的方式精确探测模型蕴含的静态知识；以及在 SFT（监督微调）和 RL（强化学习）阶段，如何通过 ChatCORE 与生成采样（Generation Sampling）来评估动态的对话质量。

理解这些指标及其背后的数学直觉，是读懂实验结果、排查训练崩溃、以及在 Leaderboard 上找准自身定位的绝对前提。

7.1 训练信号与能力信号的解耦

在传统的深度学习分类任务中（如 ResNet 分类 ImageNet），训练的 Loss 与最终的 Accuracy 往往是高度负相关的：Loss 越低，Accuracy 越高。然而，在自回归语言模型（Autoregressive Language Models）的训练中，这种简单的线性直觉被打破了。

语言模型的本质是一个极其复杂的概率分布拟合器。它在预训练阶段的目标仅仅是“预测下一个 Token”。但是，一个能够完美预测“下一个 Token”的模型，并不一定擅长解决人类定义的具体任务（如逻辑推理、数学计算或多轮对话）。这就要求我们在工程上实现评估信号的解耦：

  1. 训练底层信号（分布拟合度）：衡量模型对给定语料库的纯粹数据压缩能力。这个信号必须是高频的、极其灵敏的、且不受评测格式干扰的。在 nanochat 中，这个指标是 BPB（Bits Per Byte）。
  2. 宏观能力信号（任务解决率）：衡量模型在特定人类任务上的表现。这个信号往往是低频的、存在“涌现（Emergence）”阈值的、且高度依赖 Prompt 格式的。在 nanochat 中，这个指标是 CORE（针对 Base 模型）和 ChatCORE（针对 Chat 模型）。

Rule-of-thumb：在预训练的前 70% 时间里，请把你的目光死死盯在验证集的 BPB 上。不要因为早期 CORE 准确率停留在随机猜测水平（如四选一的 25%）就惊慌失措地停止训练。知识的提取需要底层概率分布收敛到一定程度后才会显现。

7.2 训练信号：BPB (Bits Per Byte) 的信息论视角

为什么我们不能直接比较 Loss？这是初学者最常踩的坑。

假设你在比较两个模型：模型 A 使用了词表大小为 10,000 的 Tokenizer，模型 B 使用了词表大小为 100,000 的 Tokenizer。模型 B 的 Tokenizer 切词粒度更大，一段 1000 字节的文本，模型 A 可能切成 500 个 Token，而模型 B 可能只切成 200 个 Token。

交叉熵 Loss 的计算公式为： $$ \text{Loss} = - \frac{1}{T} \sum_{i=1}^{T} \ln P(t_i \mid t_{<i}) $$ 其中 $T$ 是 Token 的总数。显然，Loss 是一个“平均每个 Token 的预测难度”的指标。由于模型 A 和模型 B 的 $T$ 完全不同，它们的概率空间也完全不同，直接比较它们的 Loss 就如同比较“平均每步走多远”来判断谁跑得快，却忽略了两人总共走了多少步。

7.2.1 BPB 的数学推导

为了获得一个绝对公平的基准，我们需要回到信息论的本源：香农熵（Shannon Entropy）。无论 Tokenizer 怎么切分，一段文本底层的客观信息量（以字节为单位）是恒定不变的。BPB（Bits Per Byte）衡量的是：为了无损地编码这段文本，平均每个字节需要消耗多少个比特（bit）的信息量。

设给定一段文本序列，其底层 UTF-8 编码的总字节数为 $B_{\text{total}}$。 经过 Tokenizer 切分后，得到 $T$ 个 Token：$t_1, t_2, \dots, t_T$。 模型对整段序列赋予的联合概率为 $P(t_1, \dots, t_T)$。根据自回归分解： $$ P(t_1, \dots, t_T) = \prod_{i=1}^{T} P(t_i \mid t_{<i}) $$ 在信息论中，对该序列进行最优编码所需的总比特数（以 2 为底的负对数）为： $$ I_{\text{total}} = - \log_2 \left( \prod_{i=1}^{T} P(t_i \mid t_{<i}) \right) = - \sum_{i=1}^{T} \log_2 P(t_i \mid t_{<i}) $$ 而我们在 PyTorch 中通常计算的交叉熵 Loss 是以自然对数 $e$ 为底的（即单位为 nats）： $$ \text{Loss}_{\text{sum}} = - \sum_{i=1}^{T} \ln P(t_i \mid t_{<i}) $$ 由于换底公式 $\log_2(x) = \frac{\ln(x)}{\ln(2)}$，我们可以将 PyTorch 的 Loss 转换为比特数： $$ I_{\text{total}} = \frac{\text{Loss}_{\text{sum}}}{\ln(2)} $$ 最终，平均每个字节的比特数（BPB）就是总比特数除以总字节数： $$ \text{BPB} = \frac{I_{\text{total}}}{B_{\text{total}}} = \frac{\text{Loss}_{\text{sum}}}{B_{\text{total}} \times \ln(2)} $$ 如果我们在批次（Batch）级别计算，假设平均每个 Token 对应的字节数为 $B_{\text{avg}} = \frac{B_{\text{total}}}{T}$，且 PyTorch 返回的是平均 Loss（即 $\text{Loss}_{\text{mean}} = \frac{\text{Loss}_{\text{sum}}}{T}$），那么公式可以简化为极其优雅的形式： $$ \text{BPB} = \frac{\text{Loss}_{\text{mean}}}{\ln(2) \times B_{\text{avg}}} $$

7.2.2 跨 Tokenizer 的绝对公平性

让我们通过一个极端的 ASCII 演示来理解 BPB 的魔力。 假设底层文本为 "Hello"，共 5 个字节（Bytes）。

【情景 1：字符级 Tokenizer】
Tokens: ["H", "e", "l", "l", "o"] (T = 5)
平均每个 Token 包含 1 个 Byte (B_avg = 1)
假设模型预测每个字符的平均 Loss = 1.386 nats
BPB = 1.386 / (0.693 * 1) = 2.0 bits/byte

【情景 2：词级 Tokenizer】
Tokens: ["Hello"] (T = 1)
平均每个 Token 包含 5 个 Bytes (B_avg = 5)
假设模型预测这个词的 Loss = 6.930 nats (注意 Loss 变大了，因为词表变大，单次预测更难)
BPB = 6.930 / (0.693 * 5) = 2.0 bits/byte

看！尽管情景 2 的 Loss（6.930）远大于情景 1 的 Loss（1.386），但经过 BPB 归一化后，两者在信息压缩的本质上是完全等价的（都是 2.0 bits/byte）。这就是为什么在 nanochat 中，所有预训练的验证指标都强制报告 BPB。

Rule-of-thumb：

  • 优秀的中文/多语言小模型，其验证集 BPB 通常在 $0.8$ 到 $1.2$ 之间。
  • 如果 BPB $> 2.0$，说明模型基本没有学到有效的语言规律（或者你的数据/掩码逻辑写错了）。
  • $\ln(2)$ 的近似值为 $0.693147$。在代码中，务必使用 math.log(2) 来保证数值精度。

7.3 能力信号：CORE 评测的非生成式探测

当 BPB 稳步下降时，我们如何知道模型是否真的掌握了“知识”，而不仅仅是死记硬背了词频？nanochat 引入了 CORE（COmprehensive Reasoning Evaluation）评测集。

对于未经指令微调（Instruction Tuning）的 Base 模型，直接让它回答问题是一场灾难。如果你输入 “法国的首都叫什么？”，Base 模型极有可能续写 “德国的首都叫什么？英国的首都叫什么？”，因为它只是在拟合互联网文本的分布，而不是在扮演一个聪明的助手。

因此，CORE 评测采用似然度评估（Likelihood Evaluation），将所有问题转化为多项选择题（Multiple Choice），并比较模型对各个选项的条件概率。

7.3.1 长度归一化的对数概率

假设我们有一个问题上下文 $C$（Context），以及四个选项 $O_1, O_2, O_3, O_4$。 模型需要计算的是：在给定上下文 $C$ 的前提下，生成选项 $O_k$ 的概率 $P(O_k \mid C)$。

如果选项 $O_k$ 被 Tokenizer 切分为一系列 Token：$o_{k,1}, o_{k,2}, \dots, o_{k,M}$，那么根据链式法则： $$ \log P(O_k \mid C) = \sum_{j=1}^{M} \log P(o_{k,j} \mid C, o_{k,<j}) $$ 这里隐藏着一个巨大的陷阱：未归一化的概率偏好短答案。 因为概率 $P \in (0, 1]$，其对数 $\log P \le 0$。这意味着，选项的 Token 数量 $M$ 越多，累加的负数就越多，总的联合概率就越小。如果选项 A 是 “巴黎”（2 个 Token），选项 B 是 “巴黎，它是法国的政治和文化中心”（15 个 Token），即使选项 B 在逻辑上更完美，模型也会因为数学上的累乘惩罚而倾向于选择选项 A。

为了解决这个问题，CORE 评测强制引入了长度归一化（Length Normalization），计算每个选项的平均 Token 对数概率作为最终得分 $S(C, O_k)$： $$ S(C, O_k) = \frac{1}{M} \sum_{j=1}^{M} \log P(o_{k,j} \mid C, o_{k,<j}) $$ 最终，模型预测的答案 $\hat{k}$ 为得分最高的选项： $$ \hat{k} = \arg\max_{k} S(C, O_k) $$

[评测引擎的内部视角]
上下文 C: "地球是太阳系由内及外的第几颗行星？\n答："

选项 A ("一"): 
  Token: ["一"] -> log P("一"|C) = -3.2 -> 得分 = -3.2 / 1 = -3.2
选项 B ("二"): 
  Token: ["二"] -> log P("二"|C) = -4.1 -> 得分 = -4.1 / 1 = -4.1
选项 C ("三"): 
  Token: ["三"] -> log P("三"|C) = -1.5 -> 得分 = -1.5 / 1 = -1.5  <-- 最大值，预测为 C
选项 D ("四"): 
  Token: ["四"] -> log P("四"|C) = -5.0 -> 得分 = -5.0 / 1 = -5.0

Rule-of-thumb：在分析 CORE 错误 case 时，如果发现模型总是选择最短的选项，请立即检查你的评测代码是否漏掉了除以选项长度 $M$ 的归一化步骤。

7.4 对话与生成评估：ChatCORE 与采样策略

当模型进入 SFT（监督微调）和 RL（强化学习）阶段后，它的输入输出不再是“任意纯文本续写”，而是被训练成在一套明确的控制 Token 边界内生成：用户消息用 <|user_start|>...<|user_end|> 包裹，助手消息用 <|assistant_start|>...<|assistant_end|> 包裹；如果引入工具，还会出现 <|python_start|>...<|python_end|> 以及由引擎注入的 <|output_start|>...<|output_end|>。这意味着评估也必须在同一格式下进行，否则你测到的不是“能力”，而是“格式偏移”。

ChatCORE 是 nanochat 的生成式评测套件。它的核心逻辑是：给定一个 Prompt，让模型自由生成一段文本，然后通过精确匹配（Exact Match, EM）或正则表达式提取出核心答案，与标准答案进行比对。

7.4.1 采样的数学与温度控制 (Temperature)

在生成文本时，模型在每一步都会输出一个词表大小的 Logits 向量 $z$。我们通过 Softmax 函数将其转换为概率分布 $P$。为了控制生成的随机性与创造性，我们引入了温度参数 $T$（Temperature）： $$ P(x_i) = \frac{\exp(z_i / T)}{\sum_{j} \exp(z_j / T)} $$

温度 $T$ 的变化对概率分布有着深远的影响：

  • 当 $T \to 0$ 时（贪心解码 Greedy Decoding）：分布变得极其尖锐。概率最大的 Token 将占据近乎 100% 的概率质量。模型每次都会确定性地选择最有可能的词。
  • 当 $T = 1$ 时（标准采样）：保留模型原始输出的概率分布。
  • 当 $T \to \infty$ 时（均匀采样）：分布变得完全平坦，所有 Token 被选中的概率趋于一致，模型将输出纯粹的乱码。
[温度 T 对概率分布的影响]
原始 Logits: [10.0, 8.0, 5.0]

T = 1.0 (标准):  P = [88.07%, 11.91%, 0.02%]
T = 0.1 (贪心):  P = [99.99%, 0.01%, 0.00%]  <- 赢家通吃
T = 5.0 (平滑):  P = [51.64%, 34.62%, 13.74%] <- 随机性增加

7.4.2 评测与推理的温差

在进行 ChatCORE 评测时，我们追求的是可复现性和模型能力上限的精确测量。在 nanochat 的采样实现（nanochat/engine.py）里，随机性主要来自“温度采样”（temperature>0）。因此评测时最稳妥的做法是直接设 $T=0$（贪心解码）：此时引擎会对每一步 logits 取 argmax，top_k 即使设置也不会改变结果（因为不会进入采样分支）。只要权重、prompt 构造与任务顺序不变，得分就应当是确定的。

然而，在实际的 Chat UI（如 scripts/chat_web.py）中与人类交互时，如果 $T=0$，模型往往会显得“干瘪”、“机械”，甚至更容易陷入重复。nanochat 的 CLI/Web 默认使用 $T\approx 0.6\sim 0.8$，并配合 top_k≈50：Top-k 的作用是只在概率最高的 K 个 token 内采样，从而压掉长尾的低概率乱码；在 Web 服务端里，top_k=0 表示不做 top-k 过滤（直接在全词表采样），并且会对温度、top-k、max tokens 做 clamp 以防滥用。

Rule-of-thumb：

  • 评测时：永远使用 $T=0$（贪心解码）。
  • 聊天时：使用 $T \in [0.6, 0.8]$，top_k≈50（需要更确定就降温度或直接设 $T=0$）。
  • 写代码/数学推导时：降低温度（例如 $T \in [0.0, 0.2]$），并可适当减小 top_k，因为这类任务容错率极低，不需要“发散探索”。

7.5 读懂 Leaderboard 与 Scaling Laws

nanochat 仓库的 dev/LEADERBOARD.md 记录了不同架构深度（d12, d24 等）、不同数据量下的模型快照表现。读懂这份排行榜，你需要建立“缩放定律（Scaling Laws）”的直觉。

  1. 算力（FLOPs）与 BPB 的帕累托前沿（Pareto Frontier）： 在 Leaderboard 上，你会观察到一条铁律：在数据质量一致的前提下，随着训练计算量的对数增加，验证集 BPB 会呈现线性的下降。如果你自己训练了一个模型，其参数量和训练 Token 数与榜单上的某个基线相当，但你的 BPB 显著高于基线（例如高出 0.2 bits/byte），这绝不是“随机波动”，这 100% 意味着你的训练代码、数据清洗或超参数存在严重 Bug。

  2. 对齐税（Alignment Tax）现象： 当你对比同一个 Base 模型和它对应的 Chat/RL 模型时，你会发现一个反直觉的现象：经过微调后，模型在下游对话任务（ChatCORE）上的得分大幅上升，但它在通用文本上的 BPB 却变差了（升高了）。 这在学术界被称为“对齐税”。因为 SFT 和 RL 强行扭曲了预训练学到的自然语言分布，使其向特定的对话模板和人类偏好靠拢。这种分布的偏移导致模型在预测普通网页文本时变得“不那么准了”。Leaderboard 上的 BPB 倒退幅度，正是衡量你微调手段是否过于激进（Overfitting）的绝佳探针。

本章小结

  • BPB（Bits Per Byte）是剥离 Tokenizer 影响后的纯粹信息压缩率指标。它是跨模型、跨实验比较的唯一真理。公式核心为：$\text{BPB} = \frac{\text{Loss}_{\text{mean}}}{\ln(2) \times B_{\text{avg}}}$。
  • CORE 评测用于 Base 模型，采用非生成的似然度评估。为了对抗数学上的累乘惩罚，必须使用长度归一化的对数概率。
  • ChatCORE 评测用于 Chat/RL 模型，采用生成后提取比对的方式。评测时务必使用贪心解码（$T=0$）以保证确定性。
  • Leaderboard 不仅是分数的堆砌，更是 Scaling Laws 的具象化。关注 BPB 的下降轨迹与对齐税的权衡，是进阶模型训练师的必修课。

练习题

  1. (基础) 为什么在自回归语言模型的训练中，交叉熵 Loss 不能用于跨词表（Cross-Vocabulary）的模型比较？ Hint：思考交叉熵 Loss 的计算分母（即序列长度 $T$）在不同 Tokenizer 下是否相同。
查看答案

交叉熵 Loss 是基于 Token 计算的，表示平均每个 Token 的预测难度。不同 Tokenizer 切分同一段文本产生的 Token 数量（序列长度 $T$）完全不同。一个切分极碎的 Tokenizer（如字符级）会产生很长的序列和较小的单步概率空间，可能得到较低的 Token-level Loss；但这不代表它的整体压缩能力更强。因此，由于概率空间和步数的不对等，直接比较 Loss 是毫无意义的。

  1. (基础) 已知模型对某个批次（Batch）计算出的平均交叉熵 Loss 为 1.386（以 $e$ 为底）。假设该批次中，平均每个 Token 对应的底层 UTF-8 字节数为 2.0。求该批次数据的 BPB。 Hint：使用公式 $\text{BPB} = \frac{\text{Loss}}{\ln(2) \times B_{\text{avg}}}$，其中 $\ln(2) \approx 0.693$。
查看答案

代入公式： BPB = 1.386 / (0.693 × 2.0) BPB = 1.386 / 1.386 BPB = 1.0 bits/byte。

  1. (基础) 在 Base 模型的 CORE 评测中，针对选项 A（2 个 Token）和选项 B（10 个 Token），如果不进行长度归一化，模型在数学上会天然倾向于选择哪一个？为什么？ Hint：概率 $P \le 1$，对数概率 $\log P \le 0$。连乘在对数空间表现为连加。
查看答案

如果不进行长度归一化，模型会天然倾向于选择选项 A（较短的选项）。因为自回归模型每生成一个 Token，都会乘以一个小于等于 1 的概率（在对数空间中则是加上一个负数）。选项 B 包含 10 个 Token，意味着要累加 10 个负对数概率，其总和通常会比只累加 2 个负对数概率的选项 A 更小（即联合概率更低）。

  1. (基础) 在进行 ChatCORE 生成式评测时，为什么强烈推荐将采样温度 $T$ 设置为 0？ Hint：考虑评测结果的方差（Variance）和实验的可复现性。
查看答案

将温度 $T$ 设置为 0 等价于贪心解码（Greedy Decoding），即在每一步都确定性地选择概率最大的 Token。这消除了采样过程中的随机性，保证了只要模型权重不变，对于相同的输入，输出总是绝对一致的。这不仅降低了评测结果的方差，也确保了实验之间的严格可比性和可复现性。

  1. (挑战) 假设一个极端的 Tokenizer 词表大小为 65536。一个未经任何训练的随机初始化模型，对所有 Token 输出均匀分布（Uniform Distribution）。如果该 Tokenizer 平均每个 Token 映射 4 个字节，求该初始状态下的 BPB。 Hint：均匀分布的概率为 $1/65536$。先求出 Loss，再转换为 BPB。
查看答案
  1. 均匀分布下，每个 Token 的预测概率 $P = 1 / 65536$。
  2. 交叉熵 Loss = $-\ln(1 / 65536) = \ln(65536) \approx 11.09$ nats。
  3. 代入 BPB 公式：BPB = 11.09 / (0.693 × 4) = 11.09 / 2.772 \approx 4.0 bits/byte。 这说明一个完全随机的、词表大小为 65536 的模型，其初始 BPB 约为 4.0。
  1. (挑战) 如果一个模型的验证集 BPB 一直在平滑下降，但 CORE 准确率却始终停留在随机猜测水平（如四选一的 25%），且直到训练结束都没有发生“涌现”，可能的原因有哪些？ Hint：从模型规模（Capacity）、数据分布（Distribution）和评测格式（Format）三个维度进行深度诊断。
查看答案
  1. 模型规模/算力不足：模型的参数量太小或训练的 Token 数不足，尚未跨越知识提取的临界阈值。此时 BPB 的下降仅仅来自于对基础语法、停用词和局部 N-gram 模式的拟合，并未建立深层的逻辑关联。
  2. 数据分布偏科：预训练语料可能全是低质量的闲聊或代码，严重缺乏与 CORE 评测集（如常识、科学、历史）相关的领域知识。
  3. 评测格式不匹配：评测时拼接上下文与选项的方式（Prompt 格式）与预训练数据的自然文本分布差异过大，导致模型在计算条件概率时处于 Out-of-Distribution (OOD) 状态，无法激活内部知识。
  1. (挑战) 在计算 BPB 时，如果数据集中包含了大量非标准的 Unicode 字符（如罕见 Emoji 或乱码），导致 Tokenizer 无法识别并将其回退为大量的 Byte Fallback Tokens，这会对最终计算出的 BPB 产生什么影响？ Hint：思考 Byte Fallback 对分子（Loss 总和）和分母（底层总字节数）的分别影响。
查看答案

底层文本的总字节数（分母）是客观存在且固定的。然而，当罕见字符被拆分为多个 Byte Fallback Tokens 时，模型对这些缺乏上下文规律的孤立字节预测往往极不准确。这会导致这些位置的交叉熵 Loss 飙升（分子变大）。由于分母不变而分子显著增加，这会大幅拉高整体的 BPB 数值。这也是为什么在预训练前进行严格的数据清洗和乱码过滤至关重要。

  1. (挑战) 为什么经过 RL（强化学习）训练后的模型，在特定任务（如 GSM8K 数学题）上的生成准确率大幅提升，但其在通用验证集上的 BPB 却往往会变差（即“对齐税” Alignment Tax）？ Hint：RL 优化的目标函数（Reward）与预训练的目标函数（极大似然估计 MLE）之间存在什么本质冲突？
查看答案

预训练的 BPB 衡量的是模型对通用自然语言分布的无偏拟合程度（极大似然估计）。而 RL 训练通过特定的奖励机制（Reward），强行扭曲了模型的输出概率空间，使其更倾向于生成符合特定任务格式（如 <step> 标签）或特定逻辑路径的文本。这种分布的剧烈偏移导致模型在面对普通的、未经格式化的自然文本时，给出的预测概率变低。在数学上表现为交叉熵 Loss 增大，从而导致 BPB 变差。这就是为了获得特定任务能力而必须支付的“对齐税”。

常见陷阱与错误 (Gotchas)

  • Gotcha 1：用 Token 级别的 Loss 向同事汇报进展。 在团队协作中，如果你说“我的模型 Loss 降到了 1.5，表现很好”，这在工程上是一句废话。因为你的同事可能在用一个词表大小完全不同的 Tokenizer。永远、绝对要使用 BPB 作为跨实验、跨团队比较语言建模能力的唯一指标。

  • Gotcha 2：评测时没有按 nanochat 对话格式渲染 prompt。 scripts/chat_eval.py 使用 tokenizer.render_for_completion() 把任务里的 conversation 渲染成 token 序列：包含 BOS、<|user_start|>...<|user_end|> 边界，并在末尾追加 <|assistant_start|> 作为待补全起点。如果你把问题当纯文本直接喂给模型，或忘了追加 <|assistant_start|>，模型会进入“格式分布外”状态，表现断崖式下跌。Chat 能力往往被封印在这种格式对齐里。

  • Gotcha 3：BPB 计算时的对数底数错误（Nats vs Bits）。 PyTorch 的 F.cross_entropy 默认以自然对数 $e$ 为底，计算出的单位是 Nats。如果你在计算 BPB 时忘记除以 $\ln(2)$（约 0.693），你算出的实际上是 Nats Per Byte。由于数值上 Nats Per Byte 比真实的 BPB 小，你会误以为自己的模型压缩率天下无敌，从而在对比 Leaderboard 时产生严重的自我认知偏差。

  • Gotcha 4：评测生成时的最大长度截断（Max New Tokens 陷阱）。 在进行 ChatCORE 采样时，如果 max_new_tokens 设置得太短，模型可能在输出关键标记之前就被截断：例如 GSM8K 的评测要在生成文本里找到 #### 后的最终数值；HumanEval 需要足够长的代码补全；多选类任务可能需要模型在末尾稳定地产生单个字母（A/B/C/D）。一旦被截断在这些关键位置之前，即使前面的推理过程看起来正确，也会被判错。务必根据任务类型为评测提供足够的生成长度预算（例如 256/512/1024）。

  • Gotcha 5：混淆 Base 评测和 Chat 评测的输入范式。 Base 评测（CORE）是计算续写选项的概率，它不需要也不应该包含 System Prompt 或对话角色标签；而 Chat 评测（ChatCORE）是要求模型生成答案，它必须严格对齐 SFT 阶段的对话格式。混用这两种范式（例如用 Chat 模板去测 Base 模型，或者用纯文本去测 Chat 模型）会导致指标完全失效，让你在排障时南辕北辙。

  • Gotcha 6：Padding Token 参与了 Loss 与 BPB 的计算。

  • Gotcha 6：Padding/特殊 Token 没有被正确排除，导致指标失真。 在构建 Batch 时，padding token 的 targets 必须被置为忽略值；在 nanochat 里，交叉熵的 ignore_index 约定是 -1。如果你忘了把 padding 对应的 labels 设为 -1，模型会大量学习“预测 padding”，从而出现一种虚假的低 loss。BPB 计算还有第二层保护：evaluate_bpb() 会用 token_bytes 把特殊 token（bytes=0）排除，并忽略所有 <0 的 targets；但如果你的 token_bytes 写错（把特殊 token 设成了非 0 bytes），BPB 也会被系统性污染。
